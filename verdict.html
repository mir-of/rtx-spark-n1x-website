09 / Verdict · 2026-11-26

它适合谁，哪些还需补测

把前八份报告收成一张选型表

N1X 不是“便宜的 4090”，也不是“全能工作站”。它的强项是 64 GiB 统一内存 + 140 W + ARM64 的本地 AI 与视频负载；短板是绝对带宽与 FP32 持续算力；游戏图形尚待实测。

00 / The short version

一台“内存很大、带宽中等、算力够用”的 ARM64 小型工作站

One paragraph

买它，是为了“把 27B 装进 140 W 的盒子里”，不是为了“跑 4K 光追”

它的 64 GiB 统一内存让 27B 级 4-bit 模型可以常驻，并且 30.5 GiB 专用 FB 内还能留下约 12 GiB 余量；它的 252 GB/s 纯读带宽决定了 30B 级稠密模型在无投机解码时的朴素解码上限大约在 8 tok/s，而 Qwen3.8-27B + MTP 实测能到 36.6 tok/s（短上下文）——这说明投机解码与模型结构能把“带宽账面”改写很多。

但它的绝对带宽只有 RTX 3090 的 24.9%、4090 的 23.1%、5090 的 13.0%；FP32 实测 19.1 TFLOPS，约为 3090 理论值的 53.7%。如果你的任务吃绝对算力或带宽，它不是一个便宜的替代品。

一句话：AI 推理、长文档、视频生成、CUDA/ARM64 开发是主场；4K 光追游戏与 FP64 HPC 尚待补测；带宽敏感 HPC 不是强项。

强项64 GiB 统一内存 + 140 W

27B IQ4_XS 峰值 18.4 GiB，FB 内仍余约 12 GiB；视频生成可把 FB 打到 30.35 GiB。

强项Tensor 与媒体能力齐全

FP16 58.9 TFLOPS、FP8 159–166、7/7 编码、6/7 解码、DLSS 5 运行时、Vulkan RT。

边界带宽与 FP32 是短板

纯读 252 GB/s；FP32 短时 19.1 / 600 s 18.0；绝对算力型任务不是强项。

02 / Fit

适合：把大模型留在本地的人

本地 27B 级推理8K 上下文 + MTP：36.6 tok/s、14.4 GiB 峰值、余量充足。适合日常对话、代码辅助、agent 循环。证据：06 推理报告 · 3.1 / 3.2
长文档批处理89K 上下文首 token 约 123 s，解码 19.3 tok/s；交互式追问靠 prompt cache，第二轮首 token 回到 0.4 s 以内。证据：06 推理报告 · 3.3 / 3.4
视频生成 / 多模态5s @1344×768 原生 8 步 15m59s；10s @1344×768 需 FreeVideo 8+3，9m37s；三组峰值 30.33–30.38 GiB。证据：07 视频报告 · 00 / 07
CUDA / ARM64 开发sm_121 在 torch 2.14.1+cu130 上直接可用；48 SM、24 MiB L2、6,144 CUDA，适合调试与小规模训练/推理。证据：01 参数 · 04；04 内存 · 09（方法与局限）
媒体前处理第九代 NVENC / 第六代 NVDEC；7/7 编码、6/7 解码；HEVC 4:2:2 10-bit 编解都通过。适合转码、超分、人脸/滤镜等 Tensor 友好负载。证据：01 参数 · 06
低功耗常驻140 W SoC TDP，AC-only mini PC；空闲 2 W / 39 °C。适合办公室、实验室桌面常驻，而不是机房。证据：01 参数 · 08（平台与 IO）；index#raw / evidence#s-smi
03 / Limits & open tests

边界与未验证：哪些场景需要补测

场景为什么需要谨慎 / 未验证更合适的方向
4K 高帧游戏、光追全开没有游戏实测；按 48 SM / 252 GB/s 与 GB7 综合分推测不理想，但不能据此下结论；后续补测。桌面独显（4090 / 5090 级）

高并发在线服务8 路并发聚合仅 2.07×，单请求降到 12.8 tok/s；每请求约 23 token 的短输出都如此，长输出更差。多卡 / MoE 专用推理卡
>40 GiB 长时间超配只测到 36 GiB × 5 min × 2 会话；>40 GiB、>10 min 未验证，不能从 5 分钟外推。更大内存的 DGX Spark / 服务器
30 分钟以上持续满载热稳态只覆盖 10–13.5 分钟；更长时间的热漂移未验证。需要长时间满载时先补测

“需补测”不等于“不能跑”。它可以在 4K 下跑游戏、可以跑 FP64 代码、可以接 8 路请求；现有证据不足以判定这些场景的性能上限。选型时应该看“单位功耗/单位成本下的有效吞吐”，而不是“能不能启动”。

06 / Open questions

仍未回答的问题

这些不是“遗漏”，而是现有证据无法覆盖的边界。对外引用时，应该把它们和结论一起说。

游戏与 DLSS 帧率

没有 3DMark / Blender / 游戏实测；DLSS 5 只验证了官方支持、NGX 运行时与 API 可用。不能把“支持 DLSS 5”当成“某游戏提升 X%”。

FP4 GEMM

PyTorch 2.14.1+cu130 没有 FP4 GEMM 路径；473.8 / 947.6 是推算。官方 1 PFLOP 是 FP4 稀疏营销口径，不是独立验证。

>40 GiB 长时间超配

只测到 36 GiB × 5 min × 2 会话；提交上限、页驱逐与系统级内存压力下的表现未覆盖。

30 分钟以上热漂移

持续负载只覆盖 10–13.5 分钟；更长时间是否降频、温度是否单调爬升，未验证。

Linux / DGX OS 对照

同一颗 GB10 在 Linux 下的统一内存上限没有在本机实测；DGX Spark 的 128 GB 与 GR1X 的 64 GiB 是两个配置。

其他模型与量化

Qwen3.8-27B IQ4_XS 的结论不外推到其他模型、其他量化或其他 llama.cpp 构建；MoE 也未在本报告复测。

07 / Closing

一句话带走

N1X 的价值不在“跑分超过谁”，而在“把 64 GiB 统一内存、140 W 和一套完整的 RTX 能力放进一个桌面小盒子”。如果你的工作负载是本地 27B 推理、长文档、视频生成或 ARM64 CUDA 开发，它是一台很合适的工作站；如果你要的是 4K 光追或 FP64 HPC，先等补测；高并发在线服务则不是它的强项。

所有数字都带口径；所有结论都能回到原始读数。这比“跑分多少”更重要。
