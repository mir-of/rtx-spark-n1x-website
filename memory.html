04 / Unified memory · 2026-11-25

64 GiB 统一内存，三个数字都成立

30.50 GiB 帧缓冲 · 45.92 GiB CUDA 配额 · 32.18 GiB 系统可见

01 / Three ceilings

三个“上限”必须分开

这不是“少了 32 GB”，而是统一内存被固件切成系统可见区与 GPU 专用帧缓冲；WDDM 再在这套划分上给出 CUDA 配额。下面几套数字同时成立，只是口径不同。

为什么 SMBIOS 写 32-bit：SMBIOS Type 17 的 Data Width / Total Width 是单个内存器件 / 模组字段；本机 LPDDR5X 为板载，WMI 只枚举到 1 个 DIMM0，所以报 32-bit。官方 256-bit 是 SoC 内存控制器侧总位宽；256 / 32 = 8，说明 WMI 报的不是总线总位宽，两者不能直接比较。

45.92 是“配额”，不是“可用容量”。它是地址空间 / 提交配额；按需提交，实际驻留受 RAM + 页文件约束。45.92 − 30.50 = 15.42 GiB 是残差，不是额外物理内存。

可用 cap_probe 夹逼：最大单次 45.75 GiB，46.0 GiB 失败，3/3 会话一致。

32.18 是“系统可见”，不是“可用给应用”。OS 自身、驱动、浏览器、桌面合成都要从这里拿。实际给大模型工作集的余量，要扣掉常驻与提交余量。

ComfyUI 日志 total RAM 32956 MB = 32.18 GiB，交叉一致。

02 / Capacity boundary

容量夹逼：45.92 是读数，45.75 是能分配

用 bench/cap_probe.py 做 0.25 GiB 步进的三会话夹逼。每次独立进程、独立上下文，结果 3/3 完全一致。

45.92 GiBcuMemGetInfo total（配额读数）三次不同负荷状态读数一致
45.75 GiB最大单次成功分配3/3 会话，0.25 GiB 步进
46.0 GiB失败点3/3 会话一致
0.17 GiB配额读数与可分配量之差45.92 − 45.75

准确写法：驱动配额读数 45.92 GiB，实际可分配 45.75 GiB（差 0.17 GiB）；持有 45.75 GiB 后连 0.25 GiB 都加不上（grow_fail=0.25）。不要把 45.92 写成“已验证可用上限”，也不要把 30.5 写成“CUDA 上限”。

注：32 GiB 分配 + 预留余量后，cuMemGetInfo 的 free 会同步下降；45.92 GiB 是上下文级配额，不是固定物理量。该配额在三次不同负荷状态（12:13 / 14:42 / 15:15）读数均为 47,021.8–47,022 MiB，在本机当前负荷区间内未观察到浮动；“会随系统内存压力浮动”是推定，未做压力实验。

07 / Mechanism

同一池内存，两层划分

第一层：固件预留。约 30.5 GiB 作为 GPU 帧缓冲，操作系统只能看到其余 32.18 GiB；余下约 1.32 GiB 为固件保留（推算值：64 − 30.50 − 32.18）。

第二层：WDDM 配额。CUDA 在“帧缓冲 + 共享预算”上拿到 45.92 GiB 的地址空间。它不是额外物理内存，而是可提交的配额；超出 FB 的页落在系统内存 / 页文件。

为什么“溢出”不一定慢。溢出页没有被搬到一条更慢的链路上：它们仍在同一组 LPDDR5X 里，只是记账科目从 Dedicated 变成了 Shared。页驻留时，GPU 以接近帧缓冲内的速度访问；真正变慢发生在页被驱逐之后——那时瓶颈是缺页与页文件，而不是带宽。

为什么 Linux 和 Windows 差这么多。同一颗 GB10，DGX Spark 上 128 GB 是一个统一池，GPU 与 CPU 共享 DRAM；iGPU 没有专用帧缓冲，nvidia-smi 甚至显示 Memory-Usage: Not Supported。Windows/WDDM 上，固件先预留约 30.5 GiB 作专用 FB，OS 只见 32.18 GiB；WDDM 再给出 CUDA 配额。所以“专用显存”语义在 Windows 上是两层叠加，不是一本账。

“64 GiB 的机器为什么只能用 45.9 GiB”不是驱动 bug，是固件划分 + Windows 内存模型共同决定的。同一台机器装 Linux 会宽松得多——但 64 GB 版本在 Linux 下也不会变成 128 GB。

打个比方：溢出不是“住得远”，是“寄人篱下”。只要还住着，速度和房东一样；房东一赶，你就得搬——搬的过程才是慢的。

45.9 GiB 是“可用容量”错是地址空间 / 提交配额；on-demand 提交，实际驻留受 RAM + 页文件约束
溢出区带宽远低于片内错（6 会话）30.5 / 31 GiB 偏移与 FB 相当（写 −0.4%、读 +1.5%）；页放置已标定
溢出区不能当工作集用部分对常驻时可用；被驱逐即退化为页文件速度，且提交余量会耗尽
08 / Engineering advice

规划口径：工作集 ≤ 30 GiB

区域建议容量用途
专用 FB（单进程 Dedicated）≤ 30 GiB热工作集：权重、KV cache、激活
溢出区（Shared）≤ 6–10 GiB冷权重、一次性加载；接受被驱逐风险
系统内存≥ 15 GiB操作系统、驱动、常驻应用
提交余量≥ 10 GB，且不超过当时提交上限的约 85%防止页文件打满导致分配失败或进程被杀
  • 保守工作集：≤ 30 GiB（单进程 Dedicated 实测封顶 29.76 GiB）。
  • 分配层面：最大单次 45.75 GiB（3/3 会话）；36 GiB 超配持续 5 分钟 × 2 会话可用（中位 122 GB/s、停顿 2–3 次），但 >40 GiB 的长时间负载未验证。
  • 推理速度：按实测纯读 252 GB/s 估，30 GB 模型理论上限约 8 tok/s（252 ÷ 30 ≈ 8.4，未含实现损耗，实际约 6）；早前用 118 / 180 / 235 推算的 4 tok/s 属口径错误，已作废。
  • 权重加载：使用 pinned 缓冲或 mmap；pageable 路径会损失 4–5 倍。
  • 超配：把最冷的数据放到溢出区，并留足提交余量；不要依赖“溢出区扛住热工作集”。

不要把“磁盘模型大小”当成“显存工作集”。本机 42 GB 模型文件（含未启用 LoRA 1.96 GB）采用顺序装卸，采样期常驻约 22.7 GiB，未接近 30.5 GiB。规划时应按框架的实际加载顺序与同时驻留峰值计算。
